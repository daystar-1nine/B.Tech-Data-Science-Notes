### Q1. Explain Cost Estimation for Selection and Join Operations in Query Optimization.

Cost estimation estimates the physical Disk Block I/O transfers using system catalog metadata (`n_r` tuples, `b_r` blocks, `V(A, r)` distinct values):

#### 1. Selection Cost Estimation (`σ_A=v(r)`):
* **Linear File Scan (No Index):** Average cost = `b_r / 2` blocks; Worst-case = `b_r` blocks.
* **Primary B+ Tree Index Lookup (Key):** `Cost = H_i + 1` block transfers (traverse index height `H_i` plus read data block).
* **Non-Key Equality with Uniform Distribution:** Expected tuples = `n_r / V(A, r)`.
  - With Clustered Index: `Cost = H_i + ⌈(n_r / V(A, r)) / f_r⌉` blocks.
  - With Secondary Index: `Cost = H_i + (n_r / V(A, r))` blocks.

#### 2. Join Cost Estimation (`r ⋈ s`):
Assume `r` is outer relation (`b_r` blocks, `n_r` tuples) and `s` is inner relation (`b_s` blocks):
* **Nested-Loop Join:** Scans `s` for every tuple of `r`.
  ```
  Cost = b_r + (n_r × b_s) block transfers
  ```
* **Block Nested-Loop Join:** Scans `s` for every disk block of `r`.
  ```
  Cost = b_r + (b_r × b_s) block transfers (reduces with M memory frames)
  ```
* **Indexed Nested-Loop Join:** Lookups using index on `s`.
  ```
  Cost = b_r + (n_r × c) block transfers (where c is index lookup cost)
  ```
* **Sort-Merge Join:** Linear merge if pre-sorted on join key.
  ```
  Cost = b_r + b_s block transfers
  ```
* **Grace Hash Join:** Partitions both tables into hash buckets, then joins in RAM.
  ```
  Cost = 3 × (b_r + b_s) block transfers
  ```

### Q2. Explain the Two-Phase Locking (2PL) Protocol, its variations, and Multiple Granularity Locking (Intent Locks).

#### 1. Two-Phase Locking (2PL):
Guarantees conflict serializability by requiring transactions to execute in two phases:
* **Growing Phase:** Transaction acquires required locks (`S` or `X`); cannot release any lock.
* **Lock Point:** The moment the transaction holds its maximum number of locks.
* **Shrinking Phase:** Transaction releases locks; cannot acquire any new lock.

#### 2. Variations of 2PL:
* **Basic 2PL:** Normal growing and shrinking phases; vulnerable to deadlocks and cascading aborts.
* **Strict 2PL:** Holds all Exclusive (`X`) locks until commit/abort. Completely eliminates cascading aborts!
* **Rigorous 2PL:** Holds all Shared (`S`) and Exclusive (`X`) locks until commit/abort. Commit order determines serial order.

#### 3. Multiple Granularity Locking (MGL):
Organizes data items into a tree hierarchy (`Database → Tablespace → Table → Page → Record`). To prevent locking conflicts, transactions acquire **Intent Locks** on ancestor nodes before locking fine-grained leaves:
* **Intent Shared (`IS`):** Signals intention to acquire `S` locks at lower levels.
* **Intent Exclusive (`IX`):** Signals intention to acquire `X` locks at lower levels.
* **Shared with Intent Exclusive (`SIX`):** Current subtree locked in `S` mode, with explicit `X` locks at lower levels.

### Q3. Explain the Timestamp Ordering Protocol, Read/Write Rules, and the Thomas Write Rule.

Assigns unique monotonic timestamp `TS(T_i)` to each transaction. Each data item `Q` maintains Write Timestamp `W-TS(Q)` and Read Timestamp `R-TS(Q)`:

#### Operational Rules:
1. **When `T_i` executes `Read(Q)`:**
   - If `TS(T_i) < W-TS(Q)`: Data has already been overwritten by a younger transaction. **Abort and Rollback `T_i`**.
   - If `TS(T_i) ≥ W-TS(Q)`: Read is valid. Execute read and update `R-TS(Q) = max(R-TS(Q), TS(T_i))`.
2. **When `T_i` executes `Write(Q)`:**
   - If `TS(T_i) < R-TS(Q)`: A younger transaction already read the old value. **Abort and Rollback `T_i`**.
   - If `TS(T_i) < W-TS(Q)`:
     - *Standard TO:* **Abort and Rollback `T_i`**.
     - *Thomas Write Rule:* **Silently ignore the write and continue!** The write is obsolete because a younger transaction already wrote `Q`, preserving view serializability.
   - Otherwise: Execute write and update `W-TS(Q) = TS(T_i)`.
* **Advantage:** Protocol is **100% Deadlock-Free** because transactions never wait for locks!

### Q4. Differentiate between Deferred Database Modification and Immediate Database Modification.

| Feature | Deferred Modification (NO-UNDO / REDO) | Immediate Modification (UNDO / REDO) |
| :--- | :--- | :--- |
| **Disk Write Timing** | Postponed strictly until **AFTER** commit point. | Allowed dynamically while transaction is **ACTIVE**. |
| **Log Record Structure** | `<Ti, X, V_new>` (Only new values needed). | `<Ti, X, V_old, V_new>` (Both old and new values needed). |
| **Recovery Operations** | **REDO Only** (Uncommitted changes never hit disk). | **Both UNDO and REDO** required. |
| **RAM Buffer Pressure** | High (All modified blocks held in memory). | Low (Dirty blocks flushed to disk via buffer pool LRU). |
| **Crash Restart Overhead** | Faster restart (no undo pass needed). | Slower restart (must undo active transactions). |
| **Standard Usage** | Embedded/specialized lightweight databases. | Standard in enterprise DBMSs (PostgreSQL, MySQL, Oracle). |

### Q5. Explain the Two-Phase Commit (2PC) Protocol for Distributed Transactions.

The 2PC protocol coordinates global transactions across multiple autonomous sites to guarantee **Global Atomicity**:

```
COORDINATOR NODE                                PARTICIPANT NODES
      |                                                 |
      | ============= 1. PREPARE =====================> |
      |                                                 | (Flush log records to disk)
      | <------------ VOTE_COMMIT / VOTE_ABORT -------- |
      |                                                 |
      | (If ALL vote COMMIT):                           |
      | ============= 2. GLOBAL COMMIT ===============> |
      |                                                 | (Commit locally)
      | <------------ ACKNOWLEDGEMENT ----------------- |
```

1. **Phase 1 (Prepare / Voting Phase):**
   - Coordinator logs `<prepare T>` and broadcasts `PREPARE` to all participant sites.
   - Each participant verifies resources: flushes undo/redo log and replies `VOTE_COMMIT` (enters Prepared state), or aborts and replies `VOTE_ABORT`.
2. **Phase 2 (Commit / Decision Phase):**
   - If **ALL** participants vote `COMMIT`: Coordinator logs `<commit T>` and broadcasts `GLOBAL_COMMIT`. Participants commit locally and send `ACK`.
   - If **ANY** participant votes `ABORT` (or times out): Coordinator logs `<abort T>` and broadcasts `GLOBAL_ABORT`. Participants roll back locally and send `ACK`.
* **The Blocking Problem:** If the coordinator crashes while participants are in the Prepared state, participants are **blocked** holding locks indefinitely until coordinator recovers.

### Q6. Explain the Precedence Graph Method to Test Conflict Serializability with an Example.

A **Precedence Graph** is a directed graph `G = (V, E)`:
* **Vertices (`V`):** Transactions in the schedule.
* **Edges (`E`):** Draw directed edge `T_i → T_j` if `T_i` accesses an item before `T_j` accesses it with at least one operation being a `Write`.

#### Example Schedule `S`:
```
Time   T1         T2
 1   Read(X)
 2              Write(X)   --> T1 Read before T2 Write ==> Edge: T1 -> T2
 3   Write(Y)
 4              Read(Y)    --> T1 Write before T2 Read ==> Edge: T1 -> T2
```

```
PRECEDENCE GRAPH:
      [ T1 ] --------------> [ T2 ]
```
* **Evaluation:** Contains **NO CYCLES (is a DAG)**.
* **Theorem:** A schedule is conflict serializable **if and only if its precedence graph contains NO CYCLES**.
* **Equivalent Serial Order:** Obtained via **Topological Sorting** ⇒ `T1 → T2`.
