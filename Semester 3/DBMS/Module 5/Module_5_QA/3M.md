### Q1. State and explain key Relational Algebra Equivalence Rules used in Query Optimization.

Two relational algebra expressions are equivalent (`E1 ≡ E2`) if they produce identical results on any valid database state:

1. **Commutativity of Selection:**
   `σ_θ1(σ_θ2(E)) ≡ σ_θ2(σ_θ1(E))`
2. **Cascading (Conjunction) of Selection:**
   `σ_(θ1 ∧ θ2)(E) ≡ σ_θ1(σ_θ2(E))`
3. **Commutativity of Join:**
   `E1 ⋈_θ E2 ≡ E2 ⋈_θ E1`
4. **Pushing Selections Down Through Joins:**
   `σ_θ0(E1 ⋈ E2) ≡ (σ_θ0(E1)) ⋈ E2` *(if condition `θ0` involves attributes only from `E1`)*. Filters rows before expensive joins!

### Q2. Draw and explain the Transaction State Transition Diagram.

```
                 +----------------------+
                 |        ACTIVE        |  <-- Executing operations
                 +----------------------+
                  /                    \
   Normal finish /                      \ Operation failure / System abort
                v                        v
     +--------------------+     +--------------------+
     | PARTIALLY COMMITTED|     |       FAILED       |
     +--------------------+     +--------------------+
                |                          |
    Commit log  |                          | Recovery manager rolls back
    flushed     |                          | dirty modifications
                v                          v
     +--------------------+     +--------------------+
     |     COMMITTED      |     |      ABORTED       |
     +--------------------+     +--------------------+
```

* **Active:** Initial state during `Read`/`Write` execution.
* **Partially Committed:** Final statement finished, but updates still in volatile RAM buffers.
* **Committed:** `<T, commit>` safely written to disk; updates are permanent.
* **Failed:** Error encountered; normal execution terminates.
* **Aborted:** Database restored to pre-transaction state; locks released.

### Q3. Differentiate between Strict 2PL and Rigorous 2PL.

| Feature | Strict 2PL | Rigorous 2PL |
| :--- | :--- | :--- |
| **Exclusive Locks (`X`)** | Held strictly until Transaction Commit or Abort. | Held strictly until Transaction Commit or Abort. |
| **Shared Locks (`S`)** | Released gradually during the Shrinking Phase. | Held strictly until Transaction Commit or Abort. |
| **Cascading Aborts** | Completely prevented (guarantees cascadeless schedules). | Completely prevented (guarantees cascadeless schedules). |
| **Serialization Order** | Determined by the chronological sequence of lock points. | Identical to the exact chronological order of transaction commit! |
| **Commercial Usage** | Used in specialized transaction managers. | **Standard default** in relational DBMSs (PostgreSQL, MySQL). |

### Q4. Explain the Validation-Based (Optimistic) Concurrency Control Protocol.

Validation-based protocol assumes conflicts are rare (read-heavy workloads) and executes in 3 sequential phases:
1. **Read Phase:** The transaction reads values from the shared database, but writes updates **only into a private local workspace memory**.
2. **Validation Phase:** The DBMS tests whether the transaction's updates conflict with any concurrent committed transactions (`Writeset(Tk) ∩ Readset(Ti) = ∅`).
3. **Write Phase:** If validation succeeds, private workspace updates are copied permanently to the database. If validation fails, the workspace is discarded and the transaction restarts.

### Q5. Explain the Write-Ahead Logging (WAL) Protocol and its two rules.

Write-Ahead Logging guarantees **Atomicity and Durability** by mandating that log records are written to stable storage before database pages:
1. **The Undo Rule (WAL-1):** Before a modified dirty data block in RAM can be written to disk, the log record containing the item's old value (`V_old`) must be flushed to stable log storage.
2. **The Redo Rule (WAL-2):** Before a transaction commits and acknowledges success to the user, all of its log records (including `<T, commit>`) must be flushed to stable log storage.

### Q6. Explain the Wait-Die and Wound-Wait Deadlock Prevention Schemes.

Both schemes use transaction timestamps `TS(T)` where smaller timestamps denote older transactions. Assume `T_i` requests a lock held by `T_j`:

* **Wait-Die Scheme (Non-Preemptive):**
  - If `T_i` is older (`TS(T_i) < TS(T_j)`): `T_i` is allowed to **wait**.
  - If `T_i` is younger (`TS(T_i) > TS(T_j)`): `T_i` **dies** (aborts and restarts with original timestamp).
  - *Summary:* Older waits, younger dies.

* **Wound-Wait Scheme (Preemptive):**
  - If `T_i` is older (`TS(T_i) < TS(T_j)`): `T_i` **wounds** `T_j` (`T_j` is aborted and forced to yield its lock).
  - If `T_i` is younger (`TS(T_i) > TS(T_j)`): `T_i` is allowed to **wait**.
  - *Summary:* Older wounds younger, younger waits. Incurs fewer aborts than Wait-Die.
