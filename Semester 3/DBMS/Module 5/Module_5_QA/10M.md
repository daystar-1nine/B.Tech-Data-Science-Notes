### Q1. Explain Query Optimization in detail. Describe the architecture of query processing, relational algebra equivalence rules, cost estimation formulas for joins, and the heuristic query optimization algorithm with a concrete before-and-after query tree example.

#### 1. Architecture of Query Processing
Query processing converts declarative SQL queries into low-level physical disk access plans:
1. **Parsing & Translation:** Checks SQL syntax/semantics against the DBMS system catalog and translates the query into an initial canonical Relational Algebra (RA) Expression Tree.
2. **Query Optimizer:** Transforms the RA tree using **Equivalence Rules**, applies **Heuristic Optimization** (pushing filters down), and uses **Cost Estimation** based on catalog statistics (`n_r, b_r, V(A,r)`) to choose the physical join and scan operators.
3. **Execution Engine:** Executes the compiled physical plan against database disk blocks.

```
SQL Query → [ Parser & Translator ] → RA Tree → [ Query Optimizer ] → Physical Plan → [ Execution Engine ]
```

---

#### 2. Key Relational Algebra Equivalence Rules
Two expressions `E1` and `E2` are equivalent (`E1 ≡ E2`) if they produce identical tuples across all valid database states:
* **Commutativity of Selection:** `σ_θ1(σ_θ2(E)) ≡ σ_θ2(σ_θ1(E))`
* **Cascading Selection:** `σ_(θ1 ∧ θ2)(E) ≡ σ_θ1(σ_θ2(E))`
* **Commutativity of Join:** `E1 ⋈_θ E2 ≡ E2 ⋈_θ E1`
* **Associativity of Join:** `(E1 ⋈ E2) ⋈ E3 ≡ E1 ⋈ (E2 ⋈ E3)`
* **Pushing Selection Down Through Join:** `σ_θ0(E1 ⋈ E2) ≡ (σ_θ0(E1)) ⋈ E2` *(when condition θ0 involves only attributes of E1)*.
* **Pushing Projection Down Through Join:** `π_(L1 ∪ L2)(E1 ⋈ E2) ≡ π_(L1 ∪ L2)(π_(L1 ∪ J)(E1) ⋈ π_(L2 ∪ J)(E2))`
* **Cartesian Product with Selection to Theta Join:** `σ_θ(E1 × E2) ≡ E1 ⋈_θ E2`

---

#### 3. Join Cost Estimation Formulas (`r ⋈ s`)
Assuming `r` is outer relation (`b_r` blocks, `n_r` tuples) and `s` is inner relation (`b_s` blocks):
* **Nested-Loop Join:** `Cost = b_r + (n_r × b_s)` block transfers.
* **Block Nested-Loop Join:** `Cost = b_r + (b_r × b_s)` block transfers (with `M` buffer frames: `b_r + ⌈b_r / (M - 2)⌉ × b_s`).
* **Indexed Nested-Loop Join:** `Cost = b_r + (n_r × c)` block transfers *(c = index traversal cost on s)*.
* **Sort-Merge Join:** `Cost = b_r + b_s` block transfers *(if relations are pre-sorted)*.
* **Grace Hash Join:** `Cost = 3 × (b_r + b_s)` block transfers *(partitioning 2(b_r + b_s) + probe b_r + b_s)*.

---

#### 4. Heuristic Query Optimization Algorithm
1. Break down complex conjunctions into single selections using the cascading rule.
2. **Push Selections Down:** Move `σ` down the tree towards base relations to eliminate non-matching rows early.
3. **Push Projections Down:** Move `π` down to eliminate unneeded columns, reducing intermediate tuple sizes.
4. Replace Cartesian products followed by selections with direct theta joins (`⋈`).
5. Order joins so that the most selective tables are joined earliest.

---

#### 5. Concrete Query Tree Example

**SQL Query:**
```sql
SELECT Emp_Name FROM Employee JOIN Department 
ON Employee.Dept_ID = Department.Dept_ID 
WHERE Department.Dept_ID = 10 AND Employee.Salary > 50000;
```

```
CANONICAL UNOPTIMIZED QUERY TREE:               HEURISTICALLY OPTIMIZED TREE:

             π(Emp_Name)                                 π(Emp_Name)
                  |                                           |
       σ(Dept_ID=10 ∧ Salary>50000)                        ⋈ (Dept_ID)
                  |                                         /        \
              ⋈ (Dept_ID)                                  /          \
               /       \                       σ(Salary>50000)      σ(Dept_ID=10)
              /         \                             |                   |
      [ Employee ]   [ Department ]              [ Employee ]      [ Department ]
      (100,000 rows)   (50 rows)                 (Filtered: 500)   (Filtered: 1 row!)
```

* **Outcome:** The unoptimized plan joins 100,000 rows with 50 rows before filtering. The heuristically optimized plan filters `Employee` to 500 rows and `Department` to 1 row *first*, joining only `500 × 1` rows, reducing Disk I/O by orders of magnitude!

### Q2. Explain Transaction Management and Concurrency Control in detail. Cover ACID properties, concurrency anomalies, conflict serializability testing using precedence graphs, Two-Phase Locking (2PL) variations, and Multiple Granularity Locking.

#### 1. ACID Properties & Concurrency Anomalies
* **Atomicity:** All-or-nothing execution, enforced by Recovery Manager via Write-Ahead Logging (WAL).
* **Consistency:** Preserves database invariants and constraints, enforced by Integrity Subsystem.
* **Isolation:** Concurrent transactions execute without mutual interference, enforced by Concurrency Control Manager.
* **Durability:** Committed updates survive crashes, enforced by Recovery Manager redo logs.

**The 4 Concurrency Anomalies (When Isolation is Violated):**
1. **Lost Update (WW Conflict):** `T1` and `T2` write to the same item; `T2` overwrites `T1`'s write without reading it.
2. **Dirty Read (WR Conflict):** `T2` reads uncommitted updates made by `T1`; `T1` later aborts.
3. **Unrepeatable Read (RW Conflict):** `T1` reads item `X`; `T2` updates `X`; `T1` re-reads `X` and sees a different value.
4. **Phantom Read:** `T1` executes a range query; `T2` inserts a new row satisfying the predicate; `T1` repeats the query and sees phantom rows.

---

#### 2. Conflict Serializability & Precedence Graphs
Two operations conflict if they belong to different transactions, access the same item, and at least one is a `Write`.
* A schedule is **Conflict Serializable** if its **Precedence Graph (Serialization Graph)** contains **NO CYCLES (is a DAG)**.
* **Topological Sort** of the acyclic precedence graph gives the equivalent serial schedule order.

```
Schedule S:
T1: Read(X), T2: Write(X), T1: Write(Y), T2: Read(Y)

Precedence Graph:
T1 --------> T2   (No cycles! Schedule is Conflict Serializable; Serial order: T1 -> T2)
```

If `T2` had written `Y` before `T1` read `Y`, an edge `T2 → T1` would create a cycle (`T1 ⇄ T2`), rendering the schedule **non-serializable**!

---

#### 3. Two-Phase Locking (2PL) Protocol & Variations
Mandates two phases: **Growing Phase** (locks acquired, none released) and **Shrinking Phase** (locks released, none acquired). The **Lock Point** is the moment the peak number of locks is held.

```
Number of
Locks Held
   ^                    LOCK POINT
   |                        /\
   |                       /  \
   |  GROWING PHASE       /    \       SHRINKING PHASE
   |  (Acquire only)     /      \      (Release only)
   +--------------------+--------+-----------------------> Time
```

* **Basic 2PL:** Guarantees serializability, but allows deadlocks and cascading rollbacks.
* **Strict 2PL:** Holds all Exclusive (`X`) locks until Commit/Abort. Eliminates cascading rollbacks!
* **Rigorous 2PL:** Holds all Shared (`S`) and Exclusive (`X`) locks until Commit/Abort. Commit order equals serialization order. Standard in commercial database engines.

---

#### 4. Multiple Granularity Locking (MGL)
Organizes data into a hierarchy: `Database → Tablespace → Table → Page → Record`.
Transactions acquire **Intent Locks** on ancestor nodes before acquiring explicit fine-grained locks on leaves:
* **Intent Shared (`IS`):** Intention to acquire `S` locks at lower levels.
* **Intent Exclusive (`IX`):** Intention to acquire `X` locks at lower levels.
* **Shared with Intent Exclusive (`SIX`):** Subtree explicitly locked in `S` mode, with intent to acquire `X` locks on lower-level descendants.

### Q3. Explain Database Recovery Systems and Distributed Transactions in detail. Describe failure types, the Write-Ahead Logging (WAL) protocol, Deferred vs Immediate Update, Checkpointing, step-by-step Crash Recovery trace, and the Two-Phase Commit (2PC) protocol.

#### 1. Failure Classification & Storage Hierarchy
* **Transaction Failures:** Logical errors or system aborts/deadlock victims.
* **System Crashes (Soft Failures):** OS kernel crash, power cut; volatile RAM lost, non-volatile disk preserved.
* **Media Failures (Hard Failures):** Disk head crash, bad sectors; restored via RAID and mirrored backups.
* **Storage Hierarchy:** Volatile (RAM) → Non-Volatile (Disk/SSD) → Stable Storage (replicated, fault-tolerant media).

---

#### 2. Write-Ahead Logging (WAL) Protocol
1. **Undo Rule (WAL-1):** The log record containing the old value (`V_old`) must be flushed to stable log storage **BEFORE** the modified dirty database buffer block is written to disk.
2. **Redo Rule (WAL-2):** All log records for a transaction including `<T, commit>` must be flushed to stable log storage **BEFORE** commit success is acknowledged.

*Log record structure:* `<Ti, start>`, `<Ti, X, V_old, V_new>`, `<Ti, commit>`, `<Ti, abort>`.

---

#### 3. Deferred vs Immediate Database Modification
* **Deferred Modification (NO-UNDO / REDO):** Disk writes delayed until *after* commit. Log contains only `<Ti, X, V_new>`. Recovery requires **REDO only**!
* **Immediate Modification (UNDO / REDO):** Disk writes allowed at any time while active. Log contains both `<Ti, X, V_old, V_new>`. Recovery requires **both UNDO and REDO**.

---

#### 4. Checkpointing & 3-Pass Crash Recovery Algorithm
A **Checkpoint** bounds recovery scan time by periodically flushing all dirty RAM buffers and log blocks to disk and writing `<CHECKPOINT {T_active_list}>`.

**3-Pass Recovery Procedure:**
1. **Analysis Pass:** Scans log backwards to most recent `<CHECKPOINT>`. Transactions with commit records are placed in the **REDO-List**; active uncommitted transactions are placed in the **UNDO-List**.
2. **REDO Pass:** Scans log forward from oldest uncommitted start. Reapplies all new values (`V_new`) for transactions in the REDO-List.
3. **UNDO Pass:** Scans log backward. Reverses all modifications (`V_old`) for transactions in the UNDO-List and writes `<Ti, abort>` records.

```
SAMPLE LOG AT CRASH:
1. <T1, start>
2. <T1, A, 100, 200>
3. <T2, start>
4. <T2, B, 50, 80>
5. <CHECKPOINT {T1, T2}>
6. <T1, commit>
7. <T3, start>
8. <T3, C, 300, 450>
9. [ SYSTEM CRASH! ]

RECOVERY EXECUTION:
* REDO-List : { T1 }       ---> Reapply A = 200
* UNDO-List : { T2, T3 }   ---> Rollback C to 300 (<T3, abort>), Rollback B to 50 (<T2, abort>)
```

---

#### 5. Two-Phase Commit (2PC) Protocol for Distributed Transactions
Ensures atomicity across distributed database sites:
* **Phase 1 (Prepare):** Coordinator writes `<prepare T>` and broadcasts `PREPARE`. Participant nodes flush logs and reply `VOTE_COMMIT` (Prepared state) or `VOTE_ABORT`.
* **Phase 2 (Commit):** If **all** voted commit, coordinator broadcasts `GLOBAL_COMMIT`; participants commit locally and send `ACK`. If any voted abort or timed out, coordinator broadcasts `GLOBAL_ABORT`; participants roll back and send `ACK`.
* **The Coordinator Blocking Problem:** If coordinator crashes during Phase 2, participants in Prepared state cannot unilaterally commit or abort and are **blocked** holding locks until coordinator recovers.
